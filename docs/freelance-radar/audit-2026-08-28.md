# Audit — false claims and assumption-based code

**Date:** 2026-08-28 · **Scope:** all of `docs/` and `src/` · **Method:** every
claim re-tested against a primary source or a live request. Nothing below is
inferred; each finding carries the command that produced it.

## Summary

| | Count |
|---|---|
| Critical — a shipped feature does not work | 2 |
| High — wrong data or false confidence | 2 |
| Medium — wrong parameters, unverified claims | 4 |
| Low — documentation drift | 3 |
| Confirmed correct (worth keeping) | 3 |

**The headline: the Discover feature has never worked and cannot have worked.**
It calls an endpoint that does not exist. This was not caught because the only
verification pass in this repo's history predates the feature by 16 days.

Everything else follows from one root cause: **`src/lib/jobDataLake.ts` was
written against a guessed API contract, and its tests were written against the
same guess.** `blockers.md` was honest that the schema was inferred; the gap is
that nothing downstream treated that as a blocker.

---

## Critical

### A1 — `searchJobs()` calls a non-existent endpoint

`src/lib/jobDataLake.ts:85` requests `/v1/jobs/search`. That path does not exist.

```console
$ curl -s "https://api.jobdatalake.com/v1/jobs/search?query=react&per_page=1"
{"error":"job not found"}          # HTTP 404

$ curl -s "https://api.jobdatalake.com/v1/jobs?query=react&per_page=1"
{"found":1786496,"page":1,"per_page":1,"jobs":[{...}]}   # HTTP 200
```

The 404 body explains the mistake: `/v1/jobs/:handle` is the single-job route,
so the router read `search` as a job handle and looked for a job called
"search". Confirmed against the published reference, which lists exactly three
endpoints — `GET /v1/jobs`, `GET /v1/jobs/:handle`, `GET /v1/companies/:handle`.
There is no search sub-path.

**Effect:** every Discover search fails. The user sees
`JobDataLake request failed (HTTP 404).` — a message that points at the API, not
at the caller, so the failure reads as the vendor's fault.

**Fix:** change the path to `/v1/jobs`. One line.

### A2 — Without a key the response is redacted to uselessness

`searchJobs()` throws unless a key is set, and `Discover.tsx:76` renders a
"Go to Settings" wall. Both assume a key is mandatory. It is not — the API
serves keyless traffic at 500 calls/day. But the keyless response omits every
field a lead needs:

```console
$ curl -s "https://api.jobdatalake.com/v1/jobs?query=react&per_page=1"
{"title": "Account Manager - Customer Retention & Upselling | Remote",
 "posted_at": 1787920509858, "first_seen_at": 1787920508000,
 "locations": ["South Africa","Philippines","Zimbabwe"],
 "job_function": "sales", "role": "Account Manager"}
```

No `company_name`. No `url`. No salary. No `job_handle`. Run through
`jobToLeadDraft()`, every lead becomes `businessName: "Unknown company"` with
`sourceUrl: ""` — a lead with no company and no link, which is not a lead.

**Effect:** fixing A1 alone produces a page that returns rows and creates
worthless leads. That is a worse failure than the 404, because it looks like it
worked.

**Fix:** keep the key requirement, but correct the *reason* in the UI copy —
the key buys usable fields, not access. Then verify the authenticated response
actually carries `company_name` and `url` before trusting it (task F4).

## High

### A3 — `normalizeJob()` misses two fields it cannot guess

Real field names, from the published reference and confirmed live:

```
title, company_name, domain_name, posted_at, locations, countries,
remote_type, job_function, seniority, salary_min_usd, salary_max_usd,
required_skills, employment_type, url, job_handle
```

The defensive multi-variant approach in `normalizeJob()` **worked for five of
seven** — `company_name`, `url`, `job_handle`, `salary_*_usd` and
`required_skills` are all among the variants it checks. Credit where due. Two
it could not have guessed:

| Line | Code expects | Reality | Result |
|---|---|---|---|
| `jobDataLake.ts:60` | `raw.location` (string) | `locations` (**array**) | Location is always `""` |
| `jobDataLake.ts:68` | `posted_at` is an ISO string | epoch **milliseconds** (`1787920509858`) | `String()` yields `"1787920509858"`, rendered as a date |

**Fix:** `locations.join(", ")`; `new Date(posted_at).toISOString()`.

### A4 — The tests validate the guess, not the API

`src/lib/jobDataLake.test.ts` has three passing tests. All three call
`jobToLeadDraft()` with a hand-written `JobDataLakeJob` fixture:

```ts
function makeJob(overrides = {}) {
  return { id: "...", company: "Acme Inc.", location: "Remote",
           applyUrl: "https://example.com/apply/abc12", postedAt: "2026-08-20", ... }
}
```

`normalizeJob()` — the only function that touches the real API shape, and the
only place A1/A3 could have been caught — **is never called by any test.** The
suite tests the mapping from an already-correct object into a lead, which was
never in doubt.

**Effect:** three green tests over the repo's only network integration, none of
which could fail for any of the reasons it is actually broken. This is the
finding that let A1 and A3 ship.

**Fix:** test `normalizeJob()` against a captured real response, committed as a
fixture. A recorded payload cannot drift into wishful thinking the way a
hand-written one does.

## Medium

### A5 — Query parameters are guessed too

`searchJobs()` sends `query`, `location`, `remote_type`, `employment_type`,
`posted_within`, `per_page`. The published reference documents:

| Code sends | Documented | Verdict |
|---|---|---|
| `query` | **`q`** | Wrong name (a live call with `query` still filtered, so it may be an alias — must be confirmed with a key) |
| `posted_within=24h\|7d\|30d` | **`posted_after`** (unix timestamp) | **Not a real parameter.** Silently ignored — the "posted within" filter does nothing |
| `remote_type`, `employment_type`, `location`, `per_page` | same | Correct |

Also documented and worth knowing before anyone adds salary filters:
`salary_min`/`salary_max` are **in thousands of USD**, so `150000` means $150M.

**Fix:** rename to `q`, convert `posted_within` to a `posted_after` timestamp,
add a comment recording the thousands-USD unit.

### A6 — Discover was never verified, and the report implies otherwise

`completion-report.md` describes a thorough Playwright verification pass —
"live browser verification after every phase", "zero page errors". Discover is
not in that list, and could not be:

```console
$ git log --format="%h %ad %s" --date=short -- docs/.../completion-report.md src/pages/Discover.tsx
f3a3d1d 2026-08-26 feat: add Discover page for JobDataLake job-source integration
059100c 2026-08-10 docs: add completion report for Freelance Radar autonomous build
```

The report predates the feature by 16 days. The report is not lying — it never
claims to cover Discover — but it is the repo's only verification record, so a
reader reasonably reads its assurances as covering the whole app.

**Fix:** one line in the report scoping it to phases 1–10, excluding Discover.

### A7 — Google Places is described as free without the billing requirement

`instagram-outreach-requirements.md` and `instagram-ledger.md` both say phase 4
is free at this volume. True on usage — 1,000 Enterprise calls/month covers
~20,000 places. But Google Maps Platform requires a **billing account with a
card attached** before it will issue a key at all, even to stay inside the free
cap. For a personal project with no revenue, that is a real barrier, and
omitting it makes phase 4 sound cheaper to *start* than it is.

**Fix:** state the card requirement wherever phase 4 is called free.

### A8 — `blockers.md` records a CORS risk that is resolved

The log's last entry says CORS support is "assumed likely" and names a
serverless proxy as the fallback. Measured:

```console
$ curl -D- -H "Origin: https://x.vercel.app" "https://api.jobdatalake.com/v1/jobs?query=react"
access-control-allow-origin: *
access-control-allow-headers: Content-Type, X-API-Key, Authorization
access-control-allow-methods: GET, POST, PUT, DELETE, OPTIONS
```

CORS is open and `X-API-Key` is explicitly allowed. No proxy needed, ever.

**Fix:** mark the entry resolved rather than deleting it — the reasoning stays
useful.

## Low — documentation drift

### A9 — Test count is stale

`completion-report.md` claims "34 passing tests across 5 files". Measured:

```console
$ npx vitest run
Test Files  6 passed (6)
     Tests  37 passed (37)
```

`jobDataLake.test.ts` added three after the report was written. The build claim
holds: `npx tsc -b` exits 0.

### A10 — `backlog.md` says every search burns a credit

It says searching has "no local caching of recent queries; worth adding if the
free tier's daily cap becomes a problem." The keyless tier is 500 calls/day at
no cost and a signup key adds 1,000 credits, so at manual search rates neither
limit is reachable. The caching item is speculative work aimed at a constraint
that does not exist.

### A11 — `requirements.md` amendment says a key is required

The 2026-08-26 amendment states the user "must supply their own key". Accurate
as a design choice, but written without knowing a keyless tier exists. Worth a
sentence so the choice reads as deliberate rather than forced.

## Confirmed correct

Not everything guessed was wrong, and the pattern in what survived is worth
keeping:

- **`X-API-Key` header name** — correct, independently confirmed by the API's
  own `access-control-allow-headers`.
- **Response envelope fallback** — `data.jobs ?? data.data ?? data.results`
  handles the real `{found, page, per_page, jobs, stats}` envelope correctly.
- **Multi-variant field matching** — caught 5 of 7 real field names.

The defensive style in `normalizeJob()` did its job. What failed was everything
it could not cover: the URL path, the parameter names, and a test suite that
never exercised it.

## Fix plan

Ordered so each step is verifiable before the next. **F1–F3 together are under
20 lines of change**; they are separated only because the verification differs.

| # | Fix | Finding | Effort | Verified by |
|---|---|---|---|---|
| **F1** | Endpoint `/v1/jobs/search` → `/v1/jobs` | A1 | 1 line | A search returns 200 with rows |
| **F2** | `query` → `q`; drop `posted_within`, add `posted_after` as a unix timestamp | A5 | ~5 lines | Filter changes visibly change `found` |
| **F3** | `locations.join(", ")`; `posted_at` epoch ms → ISO | A3 | ~4 lines | A lead shows a real location and a real date |
| **F4** | **Get a free key, capture one authenticated response, commit it as a fixture** | A2, A4 | 30 min, mostly waiting | `company_name` and `url` are present and non-empty |
| **F5** | Rewrite `jobDataLake.test.ts` to run `normalizeJob()` over that fixture | A4 | ~30 lines | Reverting F1–F3 turns the suite red |
| **F6** | Correct the Discover empty state: the key buys usable fields, not access | A2 | copy only | — |
| **F7** | Scope the completion report to phases 1–10; correct 34/5 → 37/6 | A6, A9 | 2 lines | — |
| **F8** | Mark the CORS entry in `blockers.md` resolved with the measured headers | A8 | 2 lines | — |
| **F9** | Note the Places billing-card requirement wherever phase 4 is called free | A7 | 2 lines | — |
| **F10** | Drop the Discover-caching backlog item, or note the limits that make it moot | A10 | 1 line | — |
| **F11** | Note in `requirements.md` that a keyless tier exists and the key is a deliberate choice | A11 | 1 line | — |

**F4 is the gate.** F1–F3 are confident fixes against published documentation,
but until one authenticated response is on disk, the field mapping is still
inference — the exact mistake this audit exists to correct. Do not mark Discover
working on the strength of F1–F3 alone.

**F5 is the one that prevents a repeat.** A committed real-response fixture is
what turns "we think the shape is X" into a test that fails when it isn't.
