# Blockers & Assumptions Log

Appended to during autonomous implementation whenever something was ambiguous and a judgment call had to be made instead of stopping to ask. One line each: what was ambiguous, what was chosen, why.

- **Lead.nextAction field editability**: requirements.md lists `nextAction` as a stored Lead field but doesn't say if it's user-editable. Chose to derive it automatically from `status` via `nextAction.ts` (the documented single source of truth) on every create/status-change, and only exposed `nextActionDate` as a user-editable form field, to avoid the label-drift problem `architecture.md` explicitly says the app was designed to prevent.
- **Pipeline Value calculation**: not defined in requirements.md. Chose sum of `estimatedValueMax ?? estimatedValueMin` across all non-archived leads excluding WON/LOST (i.e. only "still in play" leads), since a decided deal isn't pipeline anymore and a lost one never was revenue.
- **Leads "Follow-up" filter pill definition**: design.md lists it but doesn't define it. Chose: lead has at least one outreach record with a `followUpDate` on/before today and `status != 'replied'`, excluding WON/LOST leads — mirrors the Dashboard's due-today follow-up logic for consistency.
- **Dashboard follow-up quick actions ("Mark Contacted", "Reschedule", "Mark Replied", "Mark Closed")**: implementation-plan.md Phase 8 names these 4 actions without defining their exact behavior. Chose: Mark Contacted clears the outreach's `followUpDate` (reminder handled, no new draft forced); Reschedule sets a new `followUpDate` on the same outreach record; Mark Replied calls `outreach.markReplied` and advances a CONTACTED lead to REPLIED; Mark Closed sets the lead's status to LOST. All are thin wrappers around existing `db/outreach.ts`/`db/leads.ts` functions and log activity.
- **CSV/JSON import: reject-whole-file vs skip-bad-rows**: requirements.md's per-row language ("...the row is rejected with a row-numbered error") could mean skip-and-continue, but the Definition of Done says "malformed CSV/JSON import is rejected without corrupting existing data," and requirements.md also says imports must never partially/silently overwrite existing data. Chose the more conservative reading: validate the entire file first (staged, no IndexedDB writes), collect every row-numbered error, and if there is at least one error, reject the whole import and apply nothing — existing data is untouched either way.
- **CSV leads import semantics vs JSON import semantics**: requirements.md doesn't say whether either import merges or replaces. Chose: JSON import is a full-backup **restore** (replaces all 4 stores' contents, matching the "export -> wipe -> import -> restored" verification scenario in implementation-plan.md); CSV leads import is an **upsert by id** into the existing `leads` store (outreach/projects/activities untouched), since a CSV only ever contains a leads-only subset and wiping unrelated stores from a partial file would be surprising and destructive.
- **JobDataLake REST schema for the Discover feature**: the JobDataLake API is only accessible through this session's MCP tool wrapper; the underlying REST endpoint (`GET /v1/jobs/search`, `X-API-Key` header) and its JSON field names were inferred from the MCP tool's parameter names and one sample query, not from published API docs (jobdatalake.com doesn't expose docs without a signed-up key). `src/lib/jobDataLake.ts`'s `normalizeJob()` is written defensively (checks multiple plausible field-name variants) to reduce breakage risk, but the user should verify field mapping once they have a real API key and can inspect an actual response in devtools — see Amendment 2026-08-26 in `requirements.md`.
- **CORS on the JobDataLake API**: not documented; assumed likely supported (their homepage advertises a browser-based "Playground") since the Discover page calls the API directly from the client with no server-side proxy, consistent with this app's no-backend architecture. If CORS turns out to be blocked, `searchJobs()` surfaces a specific error message pointing at this as the likely cause; the fix would be adding a thin serverless proxy (e.g. a Vercel function) rather than changing the UI.
